## 〇、为什么需要这份文档

- **记忆/信息共享**靠 git 本身(commit + PR 描述)+ 团队语言文档

## 二、git 分支策略(2026-08-19 更新:main + dev 标准)

```
main(稳定,可装机验收)
  └─ dev(集成,开发者合入)
        └─ feature/xxx     开发者们(每个功能一个分支)
```

**流程:**
1. 每个功能/修复 → 从 `dev` 拉 `feature/xxx` 分支
2. 在 feature 分支开发,commit message 写清楚"改了什么、为什么"
3. 完成 → push feature → 开 PR 到 **dev**
4. 代码 review(琥珀或另一开发者)→ 合入 dev
5. 琥珀在 dev 上真机验收 → 合入 main

**铁律:**
- 不直接 push main/dev(走 PR,分支有保护)
- 每个 PR 描述:改了什么、为什么、怎么验收、依赖什么
- 冲突解决:先 rebase dev 再合,不 force push

## 三·五、跨设备协作(队友设备多样:Android / Windows / Linux)

> 队友用**任何能装 Agent 的设备**(Android/Windows/Linux),都能参与。原则:**代码走 git,设备只是终端**。

**每个队友需要:**
1. **GitHub 账号 + 加入仓库**(琥珀把队友加为 myfork 仓库 collaborator,或 fork + PR)
2. **装 Agent**(Reasonix/Operit 等,各设备都能装)
3. **git 客户端**(Android:Termux/MT;Windows:Git for Windows;Linux:自带)

**跨设备工作流(设备无关):**
```
1. git fetch myfork && git checkout -b feature/xxx myfork/dev
2. 改代码(模块域内)→ commit(清晰 message)
3. git push myfork feature/xxx
4. 开 PR 到 dev → 琥珀/他人 review → 合入
```

**注意:**
- **代码永远以 git 为准**,设备只是编辑工具;不用"我改了我发给你"这种传文件方式
- 无法本地跑 tsc/编译的设备(如手机 Android)→ 推分支后靠 GitHub CI 验证(CI 自动 tsc + 出包),PR 里看 CI 结果
- 手机设备可直接用 MT 管理器 APK MCP(8787)做静态调试/验证产物(见 开发协作习惯.md §〇〇·一)

**💰 GitHub Actions 额度(琥珀问:别人用 Actions 花谁的额度):**
- 仓库是 **public**(公开)→ GitHub Actions **完全免费不限量**,队友怎么 push 都不花钱
- 若以后仓库转 **private**(私有)→ 所有 Actions 分钟数扣**仓库所有者(琥珀)**的配额(2000 分钟/月,一次构建 ~3-5 分钟)
- 当前 public 仓库下: **放心用,不花琥珀任何额度**

## 四、模块式开发(避免代码冲突的核心)

> ⚠️ 琥珀要求:**模块式开发,避免代码冲突**。核心原则 = **每个开发者有自己的"文件域",改之前先看谁动过。**

### 文件域划分(谁负责哪些文件)
| 模块 | 文件域(建议) | 开发者 |
|---|---|---|
| **统计核心**(琥珀) | `src/core/player/stats.ts`、`src/core/stats/*` | 琥珀 |
| **AI 核心**(琥珀) | `src/core/stats/ai.ts`、`report.ts`、`schema.ts` | 琥珀 |
| **UI/前端** | `src/screens/Home/Views/Stats/*`(展示层)、`Setting/*` | 开发者 A |
| **播放/音频** | `src/core/player/*`(播放器)、`lyric.ts` | 开发者 B |
| **设置/配置** | `src/screens/Home/Views/Setting/*`、`src/config/*` | 开发者 C |
| **CI/发布** | `.github/workflows/*`、`tools/*` | 开发者 D |

### 避免冲突的硬规则
1. **改文件前先 `git log -- <文件>`** 看谁改过、改了啥(多会话协作文档 §二 已立,团队同样适用)
2. **不跨文件域改别人的文件**;必须改 → 先沟通,或开独立 commit 说明
3. **CODEOWNERS 自动拦截**:仓库已配 `.github/CODEOWNERS`,改不属于自己域的文件 → PR 必须经文件主人 review 才能合入(见仓库 .github/CODEOWNERS)
4. **同一模块并发时**:先 `git fetch dev` + rebase 再改,减少冲突
4. **冲突不可避免时**:rebase dev 解决,不 force push,不覆盖别人
5. **每个 PR 只含一个模块的改动**,方便 review 和回溯

### 模块开发的标准步骤
```bash
# 1. 拉最新
git fetch myfork
# 2. 从 dev 开分支(命名:feature/模块名)
git checkout -b feature/lyric myfork/dev
# 3. 只改自己模块域内的文件
# 4. commit(清晰 message)
git add src/xxx/你模块的文件
git commit -m "feat(lyric): 逐行高亮歌词(琥珀拍板)"
# 5. 推 + PR
git push myfork feature/lyric
```

## 四·五、开发者快速上手(给新加入的真人 · 跨设备版)

**你的设备只要能装 Agent + git,就能参与。代码走 git,设备只是编辑工具。**

### Linux / Windows(可本地跑 tsc)
```bash
# 环境
node 18+(官网下载,Windows 装 D 盘)
npm install(在 lx-lxwalnut-music-mobile/)
# 类型检查
npx tsc --noEmit
# 分支
git fetch myfork && git checkout -b feature/xxx myfork/dev
```

### Android(Termux / MT 管理器,不能本地跑 tsc)
```bash
# Termux 装 git + node
pkg install git nodejs
git fetch myfork && git checkout -b feature/xxx myfork/dev
# 改代码 → commit → push
git add 你模块的文件 && git commit -m "feat(xxx): ..." && git push myfork feature/xxx
```
- 无法本地 tsc → **靠 GitHub CI 验证**(PR 里看 CI 结果,CI 自动 tsc + 出包)
- 可用 MT 管理器 APK MCP(8787)做静态调试(见 开发协作习惯.md §〇〇·一)

### 出包/装机(谁都能测,不装 Android SDK)
- 推 feature 分支 → GitHub Actions 自动出 Debug APK
- 琥珀/有手机的人用 tools/ 脚本下载 + adb 无线装机

### 验收标准模板(琥珀定)
- 功能行为符合策划设计.md / 产品愿景与设计原则.md
- tsc 零新增错误(CI 验证)
- 真机实测通过(琥珀)
