> 详实记录见 `Windows编译链路实现.md`。动机:GitHub Actions 云端 CI 下载 APK 时 blob 签名 URL 频繁过期 + 本机网络慢,反复失败;改用内网 Windows 编译,传输快且可控。

| 项 | 结果 |
|---|---|
| **链路** | 本机 Linux(192.168.1.106)写码 → SSH/scp 传 Windows(192.168.1.102)→ npm install + gradle 编译 → APK scp 传回 → adb 无线装手机 |
| **Windows 环境** | 全在 `D:\Hoper`(琥珀定案禁 C 盘):Node 18 / JDK 17 / Android SDK(platform-tools, platforms;android-34, build-tools;34.0.0, ndk;26.1.10909125) |
| **编译** | `gradle_build.bat`(set CI=true 禁 Metro watch)→ schtasks 计划任务跑(脱离 ssh 会话)→ `assembleDebug --no-daemon` |
| **首次耗时** | 42-53 分钟(gradle 下载 200MB + 700 任务);二次快(有缓存) |
| **APK 对比** | Win 版 34,440,928 字节 vs CI 版 34,441,012 字节,**内容一致**(差 84 字节构建元数据),Win 版可信 |

## 四、踩坑记录(重要教训)

1. **本机是琥珀的本地 Lubuntu(3.7GB 内存),不是云端** —— 重操作前必须确认资源
2. **APK 编译走云端 CI**(策划文档 9.4),本地无需 JDK/Android SDK;**2026-08-09 起新增 Windows 编译链路**(内网,见 `Windows编译链路实现.md`)
3. **CI 的 Metro 缓存会导致 bundle 用旧代码** —— 功能"没生效"先查 CI 缓存,加 ASCII 标记验证最可靠
4. **ntfy.sh 免费版 250 条/天限流** —— 高频推送会撞配额,内网服务器是正解
5. **GitHub 对部分网络限速严重** —— 4 路并行分块下载(Range)可提速数倍;但 blob 签名 URL 5-10 分钟过期,下载慢会失败 → 改用 Windows 编译链路(内网快)
6. **ntfy 进度推送** —— 长任务进度 15 秒一次太吵(琥珀批评),关键节点(完成/失败)推送即可;但"拿不到大小也按固定间隔推真实字节"是硬要求
7. **Windows ssh 会话无桌面** —— exe 静默安装卡住、watch mode 起不来;用 msi/zip 免安装 + schtasks 计划任务
8. **gradle 日志缓冲** —— 重定向日志可能长时间不更新(其实在编译),判断是否卡查 java.exe CPU
