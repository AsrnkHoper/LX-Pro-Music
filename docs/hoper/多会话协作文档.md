# LX Music Pro 多会话协作文档

> 最后更新:2026-08-11
> 目的:多个 AI 会话(都叫"墨白")先后在同一个项目上工作,需要**协调规范**,避免互相覆盖、重复劳动、信息丢失。

## 〇、重要:产品的"代"= 开发阶段,不是会话序号

琥珀的 LX Music Pro 分**四个开发阶段**(代),是产品规划,不是 AI 会话编号:

| 代 | 阶段 | 内容 | 状态 |
|---|---|---|---|
| **一代** | 本地统计 | 本地埋点/统计/热力图/账本 | ✅ 基本完成(MVP) |
| **二代** | AI 分析 | 听歌报告(Endpoint/Key/五层 schema) | 🔄 开发中 |
| **三代** | AI 助手 | 小宠物,根据听歌数据安慰/聊天/推歌 | ⏳ 未开始 |
| **四代** | 社交 | 社交属性,可能需要服务器(成本压开发者,能否完成未定) | ❓ 未定 |

⚠️ 所以"一代修了 X、二代加了 Y"的正确含义是:**一代(本地统计阶段)的代码里修了 X,二代(AI 分析阶段)的代码里加了 Y**——是**同一个代码库按阶段演进**,不是多个会话抢着改同一份代码。git 提交历史是阶段的痕迹,不是会话的痕迹。

## 一、背景:为什么需要这份文档

琥珀的项目(LX Music Pro)由**多个会话接力开发**(各阶段由不同会话推进):
- 每个会话是独立的 Reasonix 会话,Agent 都叫"墨白",但**没有对方会话的记忆**
- 各会话通过**项目文件夹的 md 文档**共享上下文(策划设计.md / 开发进度报告.md / 开发协作习惯.md 等)
- 代码库按**阶段(一代本地统计→二代AI分析→三代AI助手→四代社交)**演进,同一会话可能跨多个阶段,一个阶段也可能多个会话接力
- 曾出现的问题:
  1. **改同一代码文件不协调**(如定时关闭 bug:一代阶段修的结算时机 + 二代阶段加的补差,但**补差逻辑有缺陷,直到后来深挖才发现 isPlay 分支绕过补差**)
  2. 一个会话改了文档,另一个会话不知情,继续用旧信息
  3. git 历史里提交交错,难分清哪些是哪个阶段做的

## 二、核心协调原则

1. **代码改动必须走 git,且每次改动要有清晰 commit**
   - 每个实质改动一个 commit,message 写清楚"改了什么、为什么"
   - 这样后续会话 `git log` 就能看到完整的改动脉络,不会覆盖
2. **动手前先看文档 + git 历史**
   - 新会话接手前:通读 `开发进度报告.md`(当前状态)、`开发协作习惯.md`(行为规范)、相关方案文档
   - 改文件前 `git log -- <文件>` 看这个文件被谁改过、改了什么
   - 有疑问(尤其"之前是不是修过这个 bug")先查历史,不要凭记忆或猜测
3. **文档是唯一真相源,改完代码必须同步文档**
   - 每次实质改动 → 更新 `开发进度报告.md`(最后更新时间 + 修复/新增内容)
   - 发现新根因/新踩坑 → 记入报告或对应文档
4. **遇到"修过但没生效"的 bug,先怀疑版本/覆盖,再怀疑代码**
   - 排查顺序:①当前代码里修复还在吗(git log + 读代码)→ ②手机上装的是不是含修复的版本 → ③修复逻辑本身有没有漏洞
   - 定时关闭 bug 就是教训:一代的修复在、二代的增强也在,但**逻辑有缺陷**——两层修复都只解决了表面,真正的漏洞(settleSession 的 isPlay 分支)直到三代才挖出来

## 四、交接规范(一个会话结束时)

1. **更新 `开发进度报告.md`**:最后更新时间、本次改动、当前状态、待办
2. **改动的代码已 commit**(不要留未提交的改动)
3. **新踩坑记入对应文档**(开发协作习惯.md / Windows编译链路实现.md 等)
4. **遗留问题写清楚**:哪些待真机验证、哪些是"修了但没确认"
5. 如果改动涉及多文件/多会话历史,在进度报告里说明改动脉络

## 五、给未来会话的提醒

- 你可能是第 N 个在 LX Music Pro 上工作的会话,前面已有多个会话的工作成果
- **先读文档再动手**:开发进度报告.md(状态)、开发协作习惯.md(规范)、策划设计.md(方案)
- **先查 git 再改**:`git log --oneline -15` 看最近改动,`git log -- <文件>` 看目标文件历史
- 改统计/埋点/播放相关代码,特别小心:**定时关闭、锁屏、切歌、退出**这几个场景是历史 bug 高发区,改完要想到这几个场景的回归
- 不确定就问琥珀,不要自己猜(见开发协作习惯.md)
