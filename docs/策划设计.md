## 一、项目定位

**一句话:** 让 LX Music 从"会放歌的工具"变成"开始认识你的音乐伙伴"。

- 基于**现成的 LX Music 移动端开源项目**做升级,不自研播放内核,专注加功能。
- 面向的用户群体:LX Music 既有用户——能自己折腾解锁的人,**填 API Key 不算门槛**,反而像"拥有自己的 AI"的仪式感。
- 开发方式:**Vibe Coding**。策划人负责描述画面与验收,AI 负责写码。

## 二、核心原则(所有设计的底层共识)

1. **本地管"事实",AI 管"观点"。**
   - 本地负责确定性统计:次数、时长、时间点,算法写死,零成本,永远可独立运行。
   - AI 只干一件事:喂给它统计事实,让它吐解读。它不碰歌单原件,只收"统计摘要"。
   - 好处:两头解耦。AI 挂了、Key 过期、断网,基础统计照常;AI 只是给数据"加一层温度"。

2. **BYOK(Bring Your Own Key),零服务端成本。**
   - 用户自行填写自己的 Endpoint + API Key,项目方不承担任何 AI 费用。
   - 用户用自己的模型、自己的偏好,定制化程度更高。

3. **"本地统计,云端解读",措辞要诚实。**
   - 统计数据不出门;AI 分析这一步,数据发往用户自填的 Endpoint,属于用户自愿行为。

4. **AI 分析是可选增强,不是地基。**
   - 填不填 Key 都不影响核心统计与基本体验;AI 挂了大不了少了"个性化"。

5. **Schema 锁死,版本号兜底。**
   - 编译好的代码是死的,动态解析不可靠;必须用固定 schema 约束 AI 输出。
   - 返回中带 `schema_version`(初版 = 1),将来加字段就升版本号,老数据仍可读。

6. **克制,不做冗余功能。**
   - 热力图本身就能讲故事,断签提醒、连胜记录这类花哨功能一律不做。

## 三、整体架构与数据流

```
┌─────────────────────────────────────────────────────┐
│  手机端 LX Music(升级版)                              │
│                                                     │
│  ① 播放事件埋点 ──► 本地统计层(次数/时长/时间点)       │
│      (复用现有 app_event 总线 + 播放历史数据源)         │
│                          │                          │
│                          ▼                          │
│  本地存储(AsyncStorage,经 src/plugins/storage.ts)      │
│  统计结果 + 自持的长期播放记录                          │
│                          │                          │
│  ② 用户填写 Endpoint + API Key(设置页)              │
│                          │                          │
│  ③ 本地统计整理成"一份大的标准化 JSON 请求"            │
│                          │                          │
│                          ▼                          │
│  ┌────────── 用户自选的 AI API ──────────┐          │
│  │ 每次分析都是全新对话,返回一份格式化报告 JSON │          │
│  └──────────────────────────────────────┘          │
│                          │                          │
│  ④ 按固定 schema 解析、本地存储                    │
│                          │                          │
│                          ▼                          │
│  ⑤ 展示层:概览 / 排行榜 / 时间规律 / 口味变迁 /      │
│     情绪揣摩 / 专业维度 / 年度热力图                 │
└─────────────────────────────────────────────────────┘
```

关键决策:

| 决策点 | 结论 | 理由 |
|---|---|---|
| AI 返回格式 | **结构化 JSON**,非自由文案 | App 自行排版,不把命运交给 AI 的嘴 |
| 请求/响应粒度 | **一份大的完整报告** | 每次新对话,超上下文风险极低;一次请求、一次解析、一次存储,状态管理简单 |
| Schema 策略 | **锁死字段结构 + `schema_version`** | 编译代码是死的;锁死最稳,版本号兜底未来扩展 |
| 点格子详情 | 第一版只做**当天账本**(纯本地) | AI 解读留给大报告场景,成本更低 |

## 四、本地统计层(事实层,永远可独立运行)

- 记录内容:播放次数、累计时长、播放时间点、歌曲/歌手/专辑信息。
- **✅ 数据留存方案(已定,方案 C 混合制)**:
  - 层① 每日聚合:每天一条(次数/时长/活跃度),**永久** —— 热力图、概览、时间规律的数据源
  - 层② 歌曲维度:每首歌(累计次数/首次播放/最近播放),**永久** —— 排行榜、私密档案、口味分析
  - 层③ 原始事件:每次播放明细,只留 **90 天** —— 近期细粒度分析
  - 原则:**细的忘得快,粗的记一辈子**;AI 分析只吃聚合摘要,不碰原始明细
- **✅ 统计口径(已定,方案 A+D)**:
  - 有效收听判定:**累计 ≥120s 或 ≥50%**(复用现有 scrobble 逻辑)——只用于次数/排行/活跃度
  - 时长类统计(总时长、热力图深浅、会话)按**实际播放秒数**累加,不受阈值限制
  - 逻辑:阈值管"算不算一次",不管"听了多久"
- **✅ 数据源(已实现,实现方式与早期设想不同)**:早期设想"复用播放历史 `@play_history` 聚合",实际改为**统计模块全新埋点**(监听 musicToggled/pause/playerEnded/play + 自建后台轮询;注:早期描述含 `playProgressChanged`,9.7 已明确不用它——锁屏时会停,以 9.7 为准),三表独立持久化(见 9.5/9.6 与开发进度报告);首启用 `@play_history` 回填一次初始数据。需长期数据的统计项由统计模块**自行持久化播放事件**(不受播放历史 31 天限制)。
- 统计项:
  - ✅ 总播放次数 `total_plays`、总时长 `total_duration_min`(已实现,概览页)
  - ✅ 活跃天数 `active_days`("这个月你其实只认真听了 21 天")(已实现,概览页)
  - ✅ 歌曲 / 歌手排行 `top_songs` / `top_artists`(已实现;专辑排行 `top_albums` 📋 待做)
  - 📋 24 小时热度 `hourly_heat`(发现"深夜高墙")—— 待实现(第二版 AI 时间层数据源)
  - 📋 周分布 `weekday_pattern`("周三晚上你总是听到很晚")—— 待实现(第二版 AI 时间层数据源)
  - 📋 收听会话统计 `session_stats`(平均单次时长、最长连续播放)—— 待实现
- 本地统计**不依赖任何 AI 配置**,即使从未填 Key,概览与热力图也完整可用。✅ 已达成(验证过)
- 时长口径可参考现有 scrobble 模块(累计 ≥120s 或 ≥50% 才算一次有效收听,见 9.6)。
- **✅ 入账门槛(已实现,2026-08-07 定稿)**:除有效收听外,还设"是否记入账本"门槛——**播放 ≥50% 且 ≥30 秒**才写入账本/时长/热力图(短歌听完入账,试听/快速切歌不入),见开发进度报告。
- **✅ 热力图色阶(已实现,2026-08-07 定稿)**:动态色阶——当月听歌最多那天=深红(满色),其余天按该基准线性映射;替代早期固定满色方案(24h/12h 均废弃,以动态色阶为准)。

## 五、AI 分析层(观点层)

> 📋 **本章为第二版核心,全部待实现**(MVP 已完成,未接 AI)。以下"已定"指方案定稿,非已实现。

### 5.1 请求侧

- 📋 用户在设置页填写自己的 Endpoint + API Key,App 本地保存,不上传任何第三方。
- 📋 **每次分析都是全新的对话(死规矩,绝不复用旧对话)**;App 将本地统计整理为**标准化 JSON 请求**。
- 📋 请求内只包含统计摘要,不包含歌单原件等隐私数据。
- 📋 **分层请求(已定)**:按五层 schema 按需请求——可只请求某一层(如仅时间层)。请求范围越小,AI 漏字段概率越低、上下文干扰越小。
- 📋 **瘦身原则(已定)**:喂给 AI 前只传相关字段,不相关统计不塞;数据太肥时(如年度报告)拆成按月分段分析,再让 AI 汇总。
  - 注:"上下文干扰"指**单次请求内部**数据量过肥,与跨次会话无关(跨次复用已禁止)。
- **✅ 触发时机(已定,三层递进,随版本走)**:
  - ✅ **MVP** → 手动按钮(统计页手动分析任意时段)—— 注:统计页已有入口,AI 分析按钮 📋 待第二版接
  - ✅ **第二版** → **懒触发**(2026-08-07 定稿,替代"真后台定时"):进入统计页时检查周期边界,该周期已结束且数据足够 → 提示报告已就绪,确认后生成;生成后按数据指纹缓存,数据变更才失效重算
    - 注:RN 无法可靠真后台定时(锁屏/被杀即失效),懒触发是本地 App 唯一可靠的"周期自动";"打开自动+缓存"提前到第二版一并做掉
    - **数据足够阈值(2026-08-07 琥珀拍板:收紧一档)**:
      | 周期 | 活跃天数下限 | 有效收听次数下限 |
      |---|---|---|
      | 月度 | ≥5 天 | ≥20 次 |
      | 季度 | ≥15 天 | ≥50 次 |
      | 年度 | ≥60 天 | ≥200 次 |
      - 只统计**已结束周期**的数据,不提前(保证报告数据完整);低于阈值不提醒(报告没货可写)
      - 风险:低频用户可能永远不触发——靠手动入口兜底(见下)
    - **提醒规则(2026-08-07 定稿)**:
      - 进统计页时检查一次;检查"最近一个完整周期"(1 月 2 号 → 上月 12 月、上季 Q4、去年 2025 同时到期)
      - 月/季/年同时到期 → **一条提示列出全部就绪报告,用户单选生成哪个**(克制烧 token)
      - 用户操作:点「生成」→ 生成并缓存;点「稍后」→ 本次不打扰,**下次进统计页再提醒**;点「忽略」→ **本周期不再提醒**(不烦人),报告入口仍在历史列表可随时手动生成
    - **数据指纹缓存(2026-08-07 定稿)**:指纹 = 周期内每日聚合 `日期:次数:时长` 拼接哈希,生成时存下;再次进入指纹未变 → 直接用缓存,不重复提醒(防重复烧 token);指纹变(如删某天数据)→ 缓存失效,但不自动重新提醒,只在历史报告入口标「数据有更新,可重新生成」
    - **手动入口**:统计页「历史报告」入口列出已生成报告 + 可**手动生成任意历史周期**;**手动不受阈值限制**(用户想生成就生成),自动提醒才受阈值限制
  - 📋 **后续** → 自动打开即看(懒触发 + 自动生成,免确认,可关)
  - ✅ 克制原则:BYOK 花的是用户自己的 token——只在该周期有足够新数据时才触发;重复生成前先确认;结果按数据指纹缓存(同一周期数据未变不重新生成,删数据才失效)

### v2 扩展(schema_version = 2,第二版新增,2026-08-07 定稿)

```json
{
  "schema_version": 2,
  "identity": {
    "period_name": "你的7月:深夜后摇的七月",
    "persona_tags": ["深夜后摇", "单曲循环爱好者"],
    "color": { "hex": "#2E3A5C", "name": "午夜蓝" },
    "color_note": "你的月份颜色像凌晨一点的天空"
  },
  "compare": {
    "plays_delta_pct": 43,
    "duration_delta_pct": 12,
    "new_artists_count": 5,
    "new_discoveries_count": 18,
    "genre_shift_summary": "这个月你从摇滚滑向后摇",
    "revisit_note": "今年1月你最爱《XXX》,现在它还在你的循环里吗?"
  }
}
```

- `identity`(周期身份层,AI 原创为主,可降级):`period_name` 给这个周期起名字(Spotify "Music Evolution" 式);`persona_tags` 周期人格标签(2~3 个);`color` 音乐颜色——**封面优先 + 流派兜底(2026-08-07 琥珀拍板)**:在线歌曲取 top 封面**真实主色**(引 `react-native-image-colors` 原生库取色,结果本地缓存),本地/无封面/取色失败 → 流派/调性映射(后摇=蓝紫、电子=青、民谣=暖棕,本地写死),再无 → 品牌色;`color_note` AI 一句话解释颜色(可降级)
- `compare`(跨周期对比层,本地补算为主 + AI 解读):`plays_delta_pct`/`duration_delta_pct` 与上一周期次数/时长变化百分比(本地算,下降为负);`new_artists_count`/`new_discoveries_count` 新认识的歌手/新歌数(本地算);`genre_shift_summary` 口味迁移一句话(AI 写,可降级);`revisit_note` 长期记忆回链(AI 写,可降级)——"今年1月你最爱《XXX》,现在还在循环里吗?",本地永久歌曲维度支持,大厂做不到
- 观点锚点(防"AI 不懂我"反噬——虎嗅 1289 条分享帖分析:用户最强负面情绪=标签刻板/数据失真):`insights` 每项及 AI 原创字段建议附 `data_basis` 数据依据("23点后播放占34%,比日间均值高2倍"),可选字段,缺失不阻断
- 用户自述(请求侧,不进 schema):设置页可填「称呼 + 语气偏好」,拼进请求 prompt,影响 AI 输出风格
  - **称呼**:可选文本输入,如「小琥珀」;AI 在报告/长文里用该称呼叫用户,不填则用「你」
  - **语气偏好(2026-08-07 琥珀拍板:五档单选,默认老朋友)**:
    1. 老朋友 —— 像懂你的朋友,平和温暖(默认)
    2. 毒舌 —— 犀利直球,带点损
    3. 温柔 —— 轻声细语,治愈向
    4. 极简 —— 只有数据事实,几乎不写废话
    5. 正经报告 —— 语气克制专业
  - **进请求方式**:拼进 system prompt 固定格式 `称呼:小琥珀 | 语气:毒舌 | 约束:…`
  - **防编造约束(死规矩)**:语气只影响措辞风格,不影响数据——所有数字/日期/歌名必须来自给定数据,一个都不能编;语气可以活泼,但事实必须诚实。与 schema 校验(四层补救)构成双重防线:prompt 管「别编」,校验管「漏了怎么办」
  - **存放**:与 Endpoint/API Key 一起存设置键 `common.ai*`(明文 AsyncStorage,同现有模式);`@stats_ai_config` 为衍生/缓存用途,不做主存储(以设置键为准);备份导出一并剔除

     - 基线(所有服务商通用):纯 prompt 约束——system prompt 写明"只输出 JSON,不要 Markdown 代码块",附目标 JSON 示例与字段说明
     - 增强(能力白名单,按服务商开启):OpenAI/Kimi/通义最新高配/Ollama/OpenRouter 支持端点 → 发 `response_format={"type":"json_schema",...}`;DeepSeek/通义低配/多数第三方 → 发 `response_format={"type":"json_object"}` 且 prompt 必须含 "json" 字样与示例(DeepSeek/通义强制要求,否则报错)
     - 服务商能力表(App 内置,不运行时探测):`json_schema` / `json_object` / `none` 三档
  2. **校验+重试**:App 对照必填白名单校验(JSON.parse + schema 校验);失败 → 重试 1-2 次(把坏输出贴回 prompt 让模型修复);检查 `max_tokens` 充足、`finish_reason !== "length"`、`refusal` 字段、content 为空(DeepSeek 偶发空内容)
  3. **本地补算**:事实层字段(overview/top/hourly_heat)本就是本地统计产物,AI 漏了直接用本地数据补上,内容无损失
  4. **降级展示**:观点层字段缺失 → UI 显示"该维度暂无解读",不硬填假数据;默认值兜底仅对真正可缺省的字段生效
  - 注意:默认值兜底是**最后一层保险,不是修复手段**——修复靠前两层,事实层靠本地补,观点层靠诚实降级。

## 六、大报告字段菜单(五层设计)

### 一、事实层(地基,纯本地数据,AI 仅复述)
- `total_plays` / `total_duration_min` —— 总播放次数、总时长
- `active_days` —— 活跃天数
- `top_songs` / `top_artists` / `top_albums` —— 排行榜

### 二、时间层(智能化:它在观察你)
- `hourly_heat` —— 24 小时热度,发现你的"深夜高墙"
- `weekday_pattern` —— 周几最沉迷
- `session_stats` —— 平均每次听多久、最长连续播放("你曾一口气听了 2 小时 17 分没停")
- `snooze_guess` —— 从播放行为推断作息("凌晨 1 点后还在播,大概率是没睡着")

### 三、口味层(个性化:它开始懂你)
- `genre_shift` —— 流派变迁("你从摇滚滑向了后摇")
- `new_discoveries` —— 新歌/新歌手("你这个月新认识了 12 个歌手")
- `repeat_obsession` —— 单曲循环之王("3 天里循环了 47 次")
- `abandoned_songs` —— 听一半就切掉的歌("有 8 首歌永远停在 30 秒内")
- `era_taste` —— 年代偏好("你骨子里是个 90 年代的人")

### 四、情绪层(情绪化:它揣摩你)
- `mood_estimate` —— 综合 tempo/情绪推断心情曲线
- `night_mood` / `morning_mood` —— 深夜 vs 清晨口味差异("白天听快歌提神,深夜全换慢的")
- `rainy_day_playlist` —— 识别"特殊日子的歌"("12 号那天你反复听同一首,那天是不是不太顺?")
- `comfort_songs` —— 安全屋歌曲("每次心情不好你都回去找这几首")

### 五、专业层(专业化:给懂行的你)
- `bpm_stats` —— 平均 BPM、BPM 分布(越听越快还是越听越慢)
- `key_distribution` —— 调性偏好(是不是偏爱小调)
- `energy_level` —— 能量值变化
- `listening_focus` —— 专注 vs 背景音("70% 把音乐当背景,30% 认真听")

### 六、身份与对比层(schema v2 新增,第二版)
- `identity.period_name` —— 周期命名("你的7月:深夜后摇的七月"),Spotify Music Evolution 式
- `identity.persona_tags` —— 周期人格标签(2~3 个)
- `identity.color` —— 音乐颜色(当月 top 专辑封面主色,本地可算;网易云 2025"颜色社交"验证)
- `compare.plays_delta_pct` / `duration_delta_pct` —— 跨周期对比(比 6 月多听 43%)
- `compare.new_artists_count` / `new_discoveries_count` —— 新认识的歌手/新歌数
- `compare.genre_shift_summary` / `revisit_note` —— 口味迁移一句话 / 长期记忆回链

> 重点押宝:`snooze_guess`(猜你没睡)、`comfort_songs`(安全屋)、`identity.period_name`(给周期起名字)、`compare.revisit_note`(长期记忆回链)——最不像统计、最像"它认识你"。

   - **✅ 生成方式(已定)**:AI 生成文案 + LX Music 品牌图作背景,App 本地合成(数字本地渲染,文案来自 AI)

> ③ **schema v2 返回**:五层(overview/time/taste/mood/pro)+ identity(period_name/persona_tags/color 音乐颜色)+ compare(跨周期对比 + 长期记忆回链)+ insights + **stories(每卡长文,与故事流卡片一一对应)** + poster,带 `schema_version=2`。
> ④ **漏字段四层补救**:① 预防——服务商能力白名单三层降级(基线:纯 prompt 约束;增强:json_schema 或 json_object;能力表 App 内置不运行时探测,已核实 DeepSeek 不支持 json_schema) ② 校验+重试 1-2 次(JSON.parse + 必填白名单校验,检查 max_tokens/finish_reason/refusal/空 content) ③ 本地补算(事实层字段 AI 漏了用本地数据补) ④ 降级展示(观点层缺失显示"暂无解读")。
> ⑤ **报告展示 = 故事流 + 长文并存**(逐卡规格见故事流卡片线框图.md):月 5/季 6/年 8 张卡横向翻卡,点卡展开长文;情绪卡是彩蛋(本地证据门槛:跨 ≥2 天重复 + 循环 ≥5 次,筛出 ≥2 首才出现);海报 = 末卡,主题色取音乐颜色,可保存相册(react-native-fs + MediaStore),「重新生成文案」带确认 + 频控 3 次/天。
> ⑥ **懒触发 + 指纹缓存**:进入统计页检查周期边界;数据足够阈值(月≥5天≥20次/季≥15天≥50次/年≥60天≥200次,只算已结束周期);提醒规则(多周期到期列表单选 / 稍后下次再提醒 / 忽略本周期不再提醒);指纹缓存(周期内每日聚合拼接哈希,未变不重生成);跨月兜底(监听日期变更信号,参照现有 AppState/BackgroundTimer 模式);手动入口两类(任意时段 / 完整周期,共用管线)。
> ⑦ **音乐颜色**:封面优先 + 流派兜底——`@stats_song` 的 `SongItem` 补 `picUrl`;引 `react-native-image-colors` 2.6.0(需先配置 expo-modules-core,JDK 17 构建);老数据 90 天内从 `@stats_events` 回填;取色失败/无封面 → 流派映射(后摇=蓝紫/电子=青/民谣=暖棕)→ 品牌色;取色结果缓存。
> ⑧ **私密小档案**:歌曲排行每首一行小字(循环过 47 次 / X年X月第一次听到 / N个月没点开)——本地直接生成不烧 token;仅 Top 20 批量一次请求 AI 润色;结果缓存 `@stats_song_profile`,数据变更才失效。
