### AI_API 稳定性 bug(推理模型 content 空,提交 a6d8e92)
- **现象**:同配置有时"成功"有时"失败:模型返回内容为空(finish_reason=length)
- **根因**:推理型模型(DeepSeek-R1/qwq 等)把测试请求当推理任务,先输出大段 `reasoning_content`,还没轮到 content 就撞上 `max_tokens=64` 截断 → content 空 + finish_reason=length
- **时好时坏原因**:思考长度波动,短思考时 64 token 够用,长思考时只够推理
- **修复**:① max_tokens 64→512 ② 系统提示明确"直接回复两个字,不要思考/解释/推理" ③ 解析兼容:content 空但模型有响应(有 reasoning_content 或 choices)→ 判"连接可用"(测试只验连通性,不测推理)
- **验证**:琥珀实测稳定成功 ✅

### Windows 链路调查结论(重要!后续会话必读)
- **现象**:本次 Windows 链路"耗时 16.5 分钟"且"完成"
- **真相**:编译**实际失败**,win_watch 误拉回**昨天(8/13)的旧 APK**
  - Windows 上所有 APK 时间戳 = 8/13 20:50,今天(8/14)没产出新 APK
  - gradle_build.log 只有 42 字节:"另一个进程正在使用此文件,进程无法访问" —— 日志文件被**残留的 gradle/java 进程锁住**
  - win_watch 用 `findstr BUILD` 匹配到**旧日志**里的 BUILD SUCCESSFUL → 误判成功
- **教训**:
  1. Windows 编译前**先确认没有残留 java/gradle 进程**(`Get-Process java`),有就先 taskkill
  2. 编译后**校验 APK 时间戳**是新的,不能只看"完成标志"(旧日志会误判)
  3. gradle_build.log 被锁 = 上次编译没死干净,先清进程
- **定案**:GitHub CI 为主链路(15:57 构建成功,2.5 分钟,可靠);Windows 链路为备选(需先清残留进程+校验时间戳)
